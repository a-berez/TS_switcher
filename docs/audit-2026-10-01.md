## Подтверждённые проблемы в настоящем Chromium

### 1. P1 — предпочитаемый TS не устанавливает правила перенаправления

Место: `src/background.js:50–54`, `:202–249`.

Шаги: загрузить расширение, выбрать `rating.pecheny.ru`, прочитать dynamic rules. `isRegexSupported` возвращает `{isSupported:false, reason:"syntaxError"}`. В списке остаётся только allow-правило 99; трёх redirect-правил нет. Консоль: `Rule with id 100 specifies an incorrect value for the "regexFilter" key.`

Причина: `(?!...)` в regex, который передаётся движку RE2. Ошибка только логируется, хотя настройка и cachedPreferred уже изменены. Дополнительно при таком preferred fallback подавляется, даже если перенаправление не установлено.

Направление исправления: RE2-совместимое правило redirect и отдельные приоритетные исключения auth; проверить успешную установку перед показом включённого состояния. [Chrome DNR](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest), [RE2](https://github.com/google/re2/blob/main/doc/syntax.txt).

### 2. P1 — fallback удаляется после настоящей DNS-ошибки

Место: `src/background.js:320–326`; аналогичная очистка есть в `src/background-firefox.js:247–253`, но в настоящем Firefox она не проверялась.

Шаги: preferred=off, fallback включён; запрос TS завершается `net::ERR_NAME_NOT_RESOLVED`. Запись fallback появляется, затем исчезает. Зафиксирован порядок событий:

1. `webNavigation.onErrorOccurred` с DNS-ошибкой.
2. В session storage записан URL неудачной загрузки.
3. `tabs.onUpdated` со `status: complete`, но URL всё ещё равен адресу неудавшейся TS-страницы: браузер закончил показывать собственную страницу ошибки.
4. `clearFallbackForTab` удаляет запись.

Итог: после окончания загрузки страницы ошибки попап уже не может предложить зеркало. Направление исправления: очищать состояние только по подтверждённой успешной навигации и отделять её от завершения страницы ошибки браузера.

### 3. P2 — выход с HTTP redirect не снимает login grace

Место: `src/background.js:373–376`, `src/background-firefox.js:281–284`.

Шаги: открыть `/login`, затем `/logout`, который отвечает HTTP 302 на `/`. Событие commit приходит для `/`, не `/logout`; session allowAllRequests остаётся. Chromium-сценарий выполнен реально с контролируемым ответом сервера, Firefox — на модели событий. Фактический ответ logout живых сайтов не проверен.

Следствие: после такого выхода во вкладке остаётся исключение из preferred. Оно будет мешать даже после исправления проблемы №1. Направление исправления: учитывать запрос logout до серверного перенаправления и явно определить срок жизни исключения.

### 4. P2 — открытая форма настроек сбрасывает более новое значение

Место: `src/options.js:5–12`, `:106–110`.

Шаги: открыть options с preferred=.ru; изменить preferred на .me из другого контекста расширения; в прежней форме снять только fallback. В хранилище preferred снова становится .ru. В браузерном тесте внешнее изменение делается тем же `Settings.setPreferredTsHost`, который использует попап; VM отдельно воспроизводит случай off→.ru→off.

Причина: форма не слушает изменения storage и сохраняет целиком старый снимок всех полей. Направление исправления: сохранять изменённые поля и синхронизировать открытую форму с storage.

### 5. P2 — теряется якорь при копировании и переключении

Место: `src/popup.js:113`.

`pathname + search` отбрасывает `hash`. На `/players/123/statistics?role=narrator#row` копия текущего TS не содержит `#row`. VM также подтвердил потерю при переключении TS. Сам `Sites.convertPath` корректно сохраняет fragment для TS: потеря происходит раньше.

Направление исправления: учитывать hash при чтении активного URL и построении ключей обновления попапа.

### 6. P2 — отмена перехода выдаётся за недоступность сайта

Место: `src/background.js:250–276`, `src/background-firefox.js:171–194`.

В настоящем Chromium навигация, завершённая `net::ERR_ABORTED`, оставляет fallback-запись. `details.error` вообще не проверяется. Firefox — такое же поведение в VM. Обычная отмена/замена загрузки не доказывает недоступность TS, но может создать ложное предупреждение.

Направление исправления: фильтровать причины отмены; проверять привязку fallback к актуальной навигации вкладки.

### 7. P3 — скрытый хост остаётся в открытом fallback-баннере

Место: `src/popup.js:167–173`.

При уже показанном баннере скрываем .me и вызываем обновление: три кнопки остаются тремя. Ключ кеша не включает visibleSwitchHosts. Обычные кнопки учитывают видимость, поэтому два участка UI расходятся. После переоткрытия попапа проблема исчезает.

Направление исправления: включить видимость в ключ fallback-рендера.

### 8. P3 — session-правила закрытых вкладок накапливаются

Место: `src/background.js:316–318`.

После открытия `/login` и закрытия вкладки её allowAllRequests по tabId остаётся в `getSessionRules()`. Это подтверждено реальным Chromium. Непосредственно другие вкладки не затрагиваются, но ненужные правила сохраняются до конца браузерной сессии.

Направление исправления: удалять правило grace при закрытии вкладки.

## Проблемы, воспроизведённые на модели API

### 9. P2 — параллельные записи теряют настройки и fallback другой вкладки

Место: `src/settings.js:54–64`, `:86–101`.

`save`, `setFallbackForTab`, `clearFallbackForTab` используют read-modify-write целого объекта без сериализации. Модель с двумя одновременными вызовами показывает:

- `save({fallbackOnError:false})` одновременно с выбором .ru: выбор сохраняется, fallback возвращается к true;
- два `setFallbackForTab` разных вкладок: сохраняется только вторая запись.

Это отдельная проблема от устаревшей формы: здесь конфликтуют даже частичные обновления. Реальная частота гонки в браузерах не измерялась. Направление исправления: единый сериализующий владелец настроек; для fallback независимые ключи вкладок либо сериализация изменений.

### 10. P2 — непостоянный Firefox background теряет состояние авторизации

Место: `src/background-firefox.js:22–28`, `:81–85`, `:196–213`; manifest `persistent:false`.

Модель пересоздания background показывает потерю loginGraceTabs даже с открытым `/login`; bootstrap grace не восстанавливает. Кроме того, запрос до завершения асинхронного чтения настроек пропускается с cachedPreferred=off, а тот же запрос после чтения уже перенаправляется.

Не утверждается, что эти сценарии были воспроизведены в настоящем Firefox: он не запускался. Нужна проверка выгрузки/пробуждения и хранения состояния. [Mozilla о состоянии event page](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts#record_state_changes).

### 11. P3 — значение bypass проверяется неточно в Chromium

Место: `src/background.js:43`.

Regex `[?&]ts_switcher_direct=1` совпадает и с `=10`. Firefox сравнивает значение точно с `1`. UI генерирует правильное значение, поэтому обычный сценарий не страдает; различие подтверждено проверкой regex. Нужна граница значения query-параметра.

## Сборка и выпуск

### 12. P1 для выпуска — сценарий changelog по тегу падает

Место: `.github/workflows/release.yml:66,69`.

В Bash написано `else:`, а не `else`. Важное уточнение к первичному аудиту: это не обнаруживается `bash -n`, поскольку строка трактуется как команда. Реальное исполнение проверено с подменённым `git describe`, без публикации:

- предыдущий тег есть: `else:: command not found`, exit 127;
- предыдущего тега нет: файл body_with_link.txt не создаётся, `cat` завершается exit 1.

Обе ветви соответствующего блока в `tag-from-commit.yml` проходят. Исправление — корректный Bash else и проверка исполнения обеих ветвей.

### 13. P2 до стабильного релиза — версия stable ниже beta

Место: `build.py:27–29`.

beta.7 преобразуется в `1.0.0.7`, stable 1.0.0 — в `1.0.0`, что при сравнении Chromium равно `1.0.0.0`. Такой stable не является обновлением установленной beta. Нужна монотонная нумерация manifest до публикации. [Правила Chromium](https://developer.chrome.com/docs/extensions/reference/manifest/version).

Дополнительный статический риск: `tag-from-commit.yml:44–45` повторно использует существующий тег, но собирает текущий checkout. Если тег указывает на другой commit, артефакт и тег могут разойтись. Реальная публикация не запускалась.

## Дополнительные наблюдения

`content.js:13` заменяет существующий history.state на `{}` при удалении маркера. Само стирание доказано моделью, но использование history.state живыми TS-сайтами не проверено: это условный риск, не доказанный сбой сайта.

В background остались обработчики старого временного `TS_SWITCHER_BYPASS`, который попап больше не отправляет. Дублирование browser-specific кода повышает риск расхождений; это вопрос сопровождения, а не самостоятельный отказ.

В папке есть игнорируемые PEM, CRX, CSV и ZIP; PEM не читались. Не следует пересылать всю папку, считая её тождественной отслеживаемому Git-коду. `popup.html` подключает Google Fonts; fallback хранит URL с query в session, либо local при отсутствии session. Поэтому формулировки об отсутствии внешних запросов и хранении только настроек в прежней документации неточны.

## Ограничения и следующий шаг

Не проверены: реальная авторизация/выход на восьми внешних сайтах, соответствие их текущих ID и маршрутов, Firefox в браузере, минимальные версии браузеров, магазины и удалённый CI, нативный toolbar popup и системный clipboard. Проверка DOM попапа выполнена в странице расширения при активной исходной вкладке. Попытка открыть toolbar popup через API не дала доступной Playwright страницы и не засчитана как проверка копирования.

Первый шаг исправлений — Chromium DNR, затем очистка fallback и жизненный цикл login grace. После этого устранить перезапись настроек и выполнить регрессионные сценарии в обоих браузерах. Публикация требует отдельного исправления workflow и стратегии версий. Пользователь пока запросил аудит; продуктовый код не изменён.
